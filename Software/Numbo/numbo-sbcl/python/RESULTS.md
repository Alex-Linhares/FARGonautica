# Results: the Python translation on the chapter's puzzles

Generated by `python3 python/scripts/chapter_runs.py --write` (a few seconds
on a multi-core machine). Each run is
`harness.run_config(puzzle, seed=s, max_iterations=20000)` in a fresh World,
seeds 1–20, with the parameters `init-chiffre` sets. The Python is always in
oracle mode: the shared splitmix64 RNG and double floats (`src/oracle.lisp`).

**These are the oracle's numbers too.** `python/tests/test_full_runs.py` makes
each of these 220 runs in a fresh oracle-mode SBCL process as well. It checks
that the two event streams, printed outputs and solution-checker verdicts are
equal, then rebuilds the tables below from the oracle's records and compares
them with this file.

Outcome columns, as in [`src/RESULTS.md`](../src/RESULTS.md):
- **valid**: the run prints "Done :" and `solution_checker.check_solution` accepts the decomposition.
- **invalid Done**: "Done :" through a killed block: the `kill-block` gap (`src/PORTING_NOTES.md` item 10).
- **gave up**: the coderack was still empty after the last retry.
- **capped**: still running at 20000 iterations.
- **error**: a Lisp error (the `reactivate-cyto` race, item 10).

Iterations are main-loop iterations (`*iteration*` + 1). Solutions are counted up to the order of + and x operands.

## Compared with `src/RESULTS.md` (default mode)

`src/RESULTS.md` was made by the SBCL port in its default mode, with CL's
`random` seeded by `sb-ext:seed-random-state`. Oracle mode replaces that RNG
with splitmix64, so seed *s* gives a different run in each mode. The code and
parameters are the same, so the two tables are two samples of 20 runs each
from the same program, and they should agree only up to sampling noise.

- **The rates agree within sampling noise.** The largest per-puzzle difference
  is #10, 17/20 against 20/20; Fisher's exact test gives p = 0.23 for it. For
  the totals, 180/220 against 182/220 valid, p = 0.90. The chapter's
  qualitative claims hold the same way in both modes. #1, #7 and #8 are
  solved quickly with the chapter's solutions. #9 finds the chapter's subtle
  solution. #3 is rarely solved. #10 prefers the "obvious" 6 x 22 route.
  #11 is easier than the chapter says. See `src/RESULTS.md` for the
  discussion.
- **The 1987 flaws show up on different seeds.** The kill-block gap gives 2
  invalid "Done :" here (puzzle 3 seed 8, puzzle 6 seed 9) and none in
  default seeds 1–20; default mode reaches it on puzzle 3 seed 93. The
  `reactivate-cyto` race errs on default seed 16 of puzzle 3, and on no oracle
  seed 1–20. In oracle mode, 4 of the 4180 runs of seeds 21–400 err:
  puzzle 1 seeds 40 and 323, and puzzle 3 seeds 162 and 272. The
  full-run test includes seeds 40 and 323.
- **Iteration counts** differ seed by seed but have the same orders of
  magnitude. For the puzzles every seed solves in both modes (#1, #2, #4,
  #5, #7, #8, #9), the medians are 22–68 here and 25–80 in default mode. #3 and
  #6 are solved by only 1 or 2 seeds in each mode, so their medians are
  single runs, not rates.

## `tests/chapter-runs.lisp` in oracle mode gives other numbers

Running the Lisp report in oracle mode, with
`sbcl --non-interactive --eval '(defvar cl-user::*numbo-oracle* t)' --load tests/chapter-runs.lisp`,
does **not** reproduce the table above. That script runs all 220 runs one
after the other in one SBCL image. `config` does not reset every global (the
free SETQs `min`, `liste`, ..., and the pnode codelet lists), so a run can
see state an earlier run left behind. For example, puzzle 3 seed 4 is valid
after 2704 iterations in the one-image report, but capped at 20000 when run
in a fresh process. The one-image report has 1 valid and 0 invalid runs for
#3. The Python makes every run in a fresh World. The oracle runs it is
compared with (`tests/oracle/lib/full-run.lisp`) each get a fresh process,
so the table above is the fresh-process one.
